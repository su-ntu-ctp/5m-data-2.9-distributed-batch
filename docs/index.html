Module 2.9 · Distributed Batch Processing

FreshCart just got acquired. 50 million rows became 5 billion rows across 12 countries. One laptop can't hold that anymore — this page walks through why, and how Apache Spark solves it.

Part 1 of 4

Why one computer stopped being enough.

Scenario. FreshCart's data used to fit on a single beefy machine. After the acquisition, the combined dataset is 5 billion rows across 12 countries — too big for any one machine's RAM or disk to process quickly. The industry answer, in order of invention, was Hadoop → MapReduce → Spark. Click through each era below.

The three eras

Same 3-step job — disk-heavy vs. in-memory

MapReduce writes results to disk after every step, then reads them back in for the next one. Spark keeps intermediate results in memory. Press play and watch the difference.

MapReduceread → map → disk → read → reduce → disk → read → output
Sparkread → map → reduce (all in memory) → output
Key concept

Spark isn't a bigger hammer — it's a smarter one. By keeping data in memory between steps instead of round-tripping through disk, it can be 10-100x faster than MapReduce on multi-step jobs, which is exactly what real data pipelines are.

Part 2 of 4

Spark is lazy — on purpose.

Scenario. You write taxi.select(...).filter(...).groupBy(...) on the 5-billion-row dataset. Spark does nothing yet — it just remembers the plan. Only when you call an action like .show() or .count() does it actually run. This lets Spark optimise the whole plan before touching any data.

Build a plan, then trigger it

Nothing has run yet. Every transformation you add below only extends the plan.
Key concept

Transformations (select, filter, groupBy, withColumn...) build a DAG (directed acyclic graph) and return immediately — no data moves. Actions (show, count, collect...) are what actually trigger computation across the cluster. This is the same lazy-evaluation idea from Lesson 2.8's Polars — Spark just runs it across many machines instead of one.

Part 3 of 4

Same table, three transformations.

Scenario. A tiny slice of the NYC taxi dataset from the hands-on notebook. In real life this table has hundreds of millions of rows spread across a cluster — but select, filter and groupBy work exactly the same whether it's 6 rows or 6 billion.

Pick an operation

trip_distance > miles
groupBy('payment_type').avg('fare_amount')
select — kept columns filter — rows that match groupBy — aggregated group
Key concept

select keeps only the columns you name, filter keeps only the rows matching a condition, and groupBy collapses rows into per-group summaries. Spark's DataFrame API mirrors pandas — the difference is entirely in how it executes underneath.

Part 4 of 4

One engine, three languages.

Scenario. A data analyst on your team only knows SQL. A data scientist prefers pandas syntax. You write PySpark. All three can query the exact same distributed DataFrame — Spark just compiles each of them down to the same execution plan.

Same question, three ways: "average fare by payment type"

↳ identical result, every time
Key concept

Registering a DataFrame with createOrReplaceTempView() lets you run spark.sql(...) against it, and .pandas_api() lets pandas users work in familiar syntax — all three run on the same distributed engine, so analysts and engineers can collaborate without translating each other's code.
